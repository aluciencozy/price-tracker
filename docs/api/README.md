# Shared API contract

[`openapi.json`](openapi.json) is the normative shared wire contract, using OpenAPI **3.1.0** and JSON Schema 2020-12. It covers the web and Flutter API, including the owned per-game refresh contract for issue #69. Import this file into an OpenAPI 3.1 tool. A local contract or implementation is not proof that a deployed host runs it or that a particular untested game is supported. Health responses are outside this business contract and remain unchanged. See historical contract review [#4](https://github.com/aluciencozy/price-tracker/issues/4) and model coordination [#1](https://github.com/aluciencozy/price-tracker/issues/1).

**SwaggerHub is published:** [API documentation](https://app.swaggerhub.com/apis/na-372-5a3/Price-Tracker-API/3.1.1) · [public JSON specification](https://api.swaggerhub.com/apis/na-372-5a3/Price-Tracker-API/3.1.1). ## Checks and examples

From the root, on Node 24 / npm 11:

```sh
npm ci
npm run test:contract
node docs/api/examples.mjs
```

The last command prints complete JSON HTTP exchanges: `method`, path template, headers, path/query values, request, status, response and response headers. [`examples.mjs`](examples.mjs) is the executable example source; omitted bodies mean **no body**, not JSON null. All credentials, application IDs, sessions, devices, observations and run results are illustrative offline fixtures. Only Portal 2 and Half-Life 2 identities/quotes come from the [October 26 source proof](../cheapshark-proof.json). USD 9.99 is a **dated recorded quote**, not a current/live price. Their examples are stale intentionally; the missing-offer example is illustrative, not a claim the game is unavailable. No multi-day history or provider-change time is invented. Never request the recorded purchase redirects from tests or the server.

Tests parse and validate the OpenAPI document, compile every schema with Ajv 2020-12, validate every route's successful request/response and representative errors, and reject unsafe/unknown fields, non-integer/unsafe money, missing/null confusion, invalid provider identities, purchase URLs, push payloads and inconsistent run states. They also check JSON request headers, both account CSRF contexts, pre-login cookie setup and successful polling headers. These are contract checks, **not** HTTP/service, CSRF enforcement, authorization, durable delivery or upstream integration tests. `npm test` includes them. No live network calls occur in contract tests.

All table paths below are relative to `/api`; OpenAPI contains the complete paths. JSON bodies must be objects of the documented shape; unknown body/query fields and duplicate query parameters are rejected. No coercion of JSON strings to numbers/booleans. Body limit 16 KiB; JSON content type required on body routes. Unknown fields may not be silently stripped. No owner IDs or provider/current-price/history writes from clients.

Account operations share services between namespaces, not duplicated business logic. Account/profile editing and deletion, refresh tokens, browser push, global catalog search and ordinary-user batch checks are deliberately absent. The owned refresh routes permit only one already-tracked Product per verified owner; they do not accept Product IDs, URLs, or batch selectors. Alert preferences are `enabled` and complete `{email:boolean,push:boolean}` on each tracker, not a separate global settings resource.

### Owned per-game refresh (#69)

`POST /tracked-items/{id}/refresh` requires the verified session and, for browser cookies, the current-session CSRF token and exact allowed Origin. It accepts only `{}` and derives the Product from the owned tracker. It returns `202 RefreshRequest` and a private status `Location`; repeated POSTs while active coalesce to the same request. `GET /tracked-item-refreshes/{requestId}` is visible only while the same user still owns the linked tracker. Missing, foreign, and deleted trackers/requests all return the same `404 NOT_FOUND`. The status DTO is separate from admin `PriceCheck`; it contains only the user's tracker ID, state/times, one last persisted observation, retry time, and an existing safe `ProductError`.

The durable per-user/per-tracker cooldown is **60 seconds after completion**. Another request during cooldown receives `429 RATE_LIMITED` with matching `Retry-After`; active `queued`, `running`, and resumable `deferred` polls say `Retry-After: 5`. The service uses the same single-Product check, provider-wide budget/cache/backoff, observation, episode, and delivery pipeline as scheduled/admin checks. `refreshed` means a genuine provider success recorded an observation. `cached` means a quote within the existing 24-hour success cache is backed by an actual persisted history row; it may re-evaluate that real observation after a target change, but adds no row and does not claim a new fetch. A preview-only cache is never relabeled as history; it requires a genuine bounded provider lookup before success. Target edits alone never create an observation or alert. Failures retain the last successful observation; deferred work keeps its real retry time. The client never receives the internal run, global lock, leases, other Product selections, or other watchers' details.

## Authentication and browser safety (normative)

The October 28 interview confirms persistent web sign-in, superseding older JWT-only wording in #4/#9. The web receives an **opaque** cookie secret (not the informational `sessionId`); mobile receives a JWT. Both map to revocable server-side sessions. Fixed lifetime is **604800 seconds / seven days**, with no sliding expiry or refresh endpoint. `expiresAt` is authoritative. Validate JWT signature, explicit algorithm allowlist, issuer/audience, expiry and active session/account state on every request. Unverified users never receive a session; return `403 EMAIL_UNVERIFIED` only after verifying credentials. Invalid credentials get the same generic 401. Normalize/trim email consistently server-side; never trim passwords.

Production cookie: `__Host-price_tracker_session=<opaque>; Path=/; Max-Age=604800; Expires=<matching UTC expiry>; HttpOnly; Secure; SameSite=Lax`, **no Domain**. Never send its secret/JWT in JSON, URLs, logs, localStorage or sessionStorage. On reload/reopen, bootstrap with web `me`; a 401 returns to sign-in. GETs never extend expiry. Login rotates session identity, invalidates a previous session supplied on that request (and its devices), and invalidates pre-login CSRF state. Logout revokes the current session and its device bindings server-side before 204 and clears cookies with matching attributes. Password reset atomically revokes **all** account sessions/device bindings. Every later request with a revoked token fails, even before its nominal expiry. Client clears local state on 401; never falls back to sample success. An offline logout can clear local state but cannot claim server revocation until contact succeeds.

1. Before any browser mutation, call `GET /api/auth/web/csrf` with credentials. Without a session this sets `__Host-price_tracker_prelogin`, a random HttpOnly, Secure, host-only, SameSite=Lax, Path=/ cookie expiring after **30 minutes**, and returns its bound CSRF token. With a session it returns a session-bound token expiring no later than the session; it need not set a pre-login cookie. Repeated bootstrap may return the same valid token; do not invalidate another tab unnecessarily. Reject an unapproved supplied Origin with 403 `ORIGIN_DENIED` without issuing tokens/cookies; same-origin GET bootstrap need not supply Origin.
2. Send `X-CSRF-Token` **and exact allowlisted `Origin`** on every browser mutation, including register, login, logout, verification/reset and preview. The six account forms (register, verify, resend, forgot, reset and login) accept **either** the current-session-bound token with its session cookie **or** the pre-login-bound token with its pre-login cookie. Signing in again or switching accounts does not require logging out first: validate that binding before rotating/revoking the existing session. Authenticated resource mutations and logout require the current-session binding, not merely pre-login context. Reject missing/expired/unbound tokens with 403 `CSRF_INVALID`; missing/null/unapproved origins with 403 `ORIGIN_DENIED`. Do not rely on SameSite alone. Obtain a new bootstrap after login/logout; do not automatically replay an uncertain mutation just because a CSRF token changed.
3. Web auth routes reject Authorization headers. Mobile auth/device routes reject either named web cookie, including pre-login cookies. Shared business routes reject any combination of bearer and either web cookie with 400 `AUTH_AMBIGUOUS`, even if one credential is invalid; they never choose whichever works. Namespace misuse is also `AUTH_AMBIGUOUS`. Public native account routes do not issue or accept browser cookies; do not enable credentialed browser CORS for those routes. Bearer auth is a native transport, not a browser CSRF bypass.
4. Prefer same-origin `/api` routing. Approved cross-origin web deployments must be **same-site HTTPS** (SameSite=Lax is not a cross-site deployment solution), with `credentials: include`, exact configured origins, `Access-Control-Allow-Credentials: true`, and `Vary: Origin`; never `*`, reflected arbitrary origins or suffix matching. Preflight only approved origins/methods/headers (`Content-Type`, `X-CSRF-Token`, `Idempotency-Key`; native bearer uses `Authorization`). Expose `Retry-After`/`Location` as needed. OPTIONS has no business side effect or auth requirement. Reject unapproved actual requests, not just preflight. Do not expose CSRF bootstrap to unapproved origins.
5. **Explicit local debug exception only:** HTTP on `localhost` or `127.0.0.1`, using same-origin Vite proxy where possible. Use names `price_tracker_session_dev` / `price_tracker_prelogin_dev`, same HttpOnly/host-only/Path=/SameSite=Lax/expiry policy but without Secure; never weaken a `__Host-` cookie or depend on inconsistent browser exceptions. Recognize these names as cookie auth for ambiguity rejection too. Allow only exact configured loopback origins (for example `http://127.0.0.1:5173`), not LAN/public hosts. Production must refuse this mode and require HTTPS. Native emulator `10.0.2.2` is a debug transport only, not a web-origin/cookie exception. This is policy for future implementation, not newly added environment configuration.

All auth/account responses, CSRF bootstrap, previews, private resources and errors use `Cache-Control: no-store`. Never log password, CSRF/reset/verification token, JWT, cookie or push token. Use safe request IDs instead.

### Email link handoff

Use allowlisted HTTPS web links `/verify-email#token=<secret>` and `/reset-password#token=<secret>`. Read the fragment into memory and immediately remove it with `history.replaceState`; no token query parameters, analytics, third-party scripts or referrer leakage on these pages (`Referrer-Policy: no-referrer`). Show an explicit confirmation/form. **GET never consumes tokens**; POST only after CSRF bootstrap and user action. Neither verification nor reset auto-logs in. Verification expires after 24 hours; reset after 30 minutes. Store only token hashes, enforce single use/expiry atomically; reissuing invalidates previous token of the same purpose. Generic 202 body is always `{"message":"If eligible, you will receive an email with next steps."}` for register/resend/forgot, including existing/unknown/ineligible accounts. Flutter opens/explains browser completion, then asks users to return and sign in; no app deep-link token handling is required.

## Offers, history and alerts

- `Money` is required `{amountMinor,currency:"USD"}`; amount is integer **0..9007199254740991**. Zero is valid/free; missing prices are **null**. All model keys marked required remain present even when nullable. Application IDs are opaque strings. Steam app, CheapShark game, store and changing deal IDs are separate string fields, not interchangeable integers.
- `Product` is shared metadata for `(cheapshark,providerGameId,"1","US","USD")`; `TrackedItem` is private `{id,product,targetPrice,enabled,alerts,createdAt,updatedAt}`. The public schema lists Product response fields; internal server validation metadata is not part of the DTO. Current attribution is `Prices supplied by CheapShark; exact Steam app US/USD offer, excluding taxes and checkout adjustments.` The exact prior `base-game` literal remains accepted for compatibility with legacy responses and records; arbitrary attribution strings are rejected. Preserve attribution and select **only** the exact current Steam US/USD offer. Match exact IDs, never title similarity; reject valid non-game types, missing exact matches and ambiguous matches. The current resolver discovers submitted app IDs on demand, rather than using a fixed two-game API list. Steam's undocumented `appdetails` check requires a positive result with type `game`, but that coarse type does not distinguish every special edition. The October 26 proof records only two games; dynamic discovery is not a guarantee for every app or edition.
- Parse submitted URLs locally with the URL parser and an exact Steam host/path allowlist. Do not fetch them. Preview uses the bounded Steam type check and fixed CheapShark endpoints, DNS/private-address/redirect safety, honest application User-Agent, timeout/body/concurrency limits and a shared cache/provider budget. Unsupported URL/type/content, missing exact match, ambiguity, or no qualifying Steam US/USD offer returns 422 if no validated quote can be returned. Without a retained quote, malformed/mismatched provider metadata or other provider/service failures return 503; throttling returns 429 with `Retry-After`. A prior validated quote may instead be returned as stale with failure metadata after a refresh failure. Never treat that retained price as a new current quote or observation, and never automatically fetch `/redirect`; purchase URLs are human navigation only. The API must ensure canonical app URL matches `steamAppId`. Only vetted HTTPS image origins; never turn API images into an arbitrary fetch proxy.

  For a non-null `dealId` (1–256 Unicode code points), the API and clients must compute the exact purchase URL as follows: decode existing percent encoding **once** using strict UTF-8 URI-component decoding (`decodeURIComponent` semantics), rejecting malformed escapes or invalid UTF-8; then set that decoded value as `dealID` on `new URL('/redirect', 'https://www.cheapshark.com')` using `URLSearchParams`, and serialize the URL. A raw `+` is a literal plus, not a space; a raw or encoded slash normalizes to `%2F`, a space to `+`, a plus to `%2B`, and a literal percent must be supplied as `%25`. Do not decode a second time: `%252F` normalizes to `%252F`. For example, `a%2Fb` and `a/b` both produce `https://www.cheapshark.com/redirect?dealID=a%2Fb`; `space%20and%2Bplus` produces `https://www.cheapshark.com/redirect?dealID=space+and%2Bplus`.

  Require exact string equality with this computed URL on both API and client boundaries, not just the OpenAPI pattern: the schema cannot enforce the cross-field identity or canonical encoding. This also forbids credentials, fragments, additional or duplicate query parameters, non-HTTPS, alternate hosts/ports and paths. Both fields are null together when no deal is retained. The schema retains its 4096-character URL bound and permits `+` and `*` required by form serialization; it also permits some noncanonical encodings for compatibility, which the equality check must reject. The deal ID bound is reduced from 1024 to 256 code points: even 256 four-byte characters serialize in at most 3072 query characters plus the fixed prefix, within 4096. This is a contract restriction for formerly schema-valid longer values; the existing upstream adapter already limits input to 256 UTF-16 code units, which is stricter for supplementary characters, so valid adapter input remains within the new bound. This corrects the earlier `encodeURIComponent(dealId)` rule; clients relying on it must update. Flutter's `Uri.encodeComponent` alone does not implement this normalization and needs a separate mobile follow-up.
- `observedAt` is the last successful **local** observation; `providerChangedAt` is nullable upstream change time, never inferred from fetch time. `lastAttemptAt`/`lastError` describe the latest attempt. `staleAt = observedAt + 24 hours`. `fresh` means a valid success younger than staleAt and no later failed attempt; `stale` preserves the last valid price after age/failure. `unavailable` means **no retained successful observation**, so prices, observedAt, providerChangedAt, staleAt and deal/purchase are null. A later missing offer keeps last-success metadata as stale; explain that any retained link is dated/unconfirmed. Failed fetches create neither zero prices nor history rows. Never evaluate alerts against stale failures. `nextCheckAt` is an estimate, not a delivery promise.
- Previews last 10 minutes and belong to the authenticated user. They may use a retained cached stale observation if identified honestly, but cannot fabricate an offer without a previously validated Steam success. Missing/unsupported matches get 422. Saving an owned unexpired preview does not trigger a new upstream request; worker checks refresh later. Foreign preview/item/device IDs always get 404. Never leak another user's `resourceId`.
- Lists have default limit 20, max 100, opaque `nextCursor` (null means done). Literal, case-insensitive title substring search is private watchlist-only. Cursors bind owner/filter/sort/window; malformed or changed-filter cursors return 422 `INVALID_CURSOR`. History is available **only** at an owned tracker path, ordered ascending `(observedAt,id)`; range is `[from,to)`, defaults previous 30 days, maximum 90 days, `from < to`, UTC. Subsequent cursor requests repeat returned window; cursor embeds the first page's normalized window, so omitted bounds reuse it rather than advancing "now". Proposed retention is rolling **90 days of minimal local observations**, no provider payload archive/bulk export; model/provider owners must confirm retention under #1/#14 before implementation. `retainedFrom` exposes the actual retention boundary even with no rows; older requested windows may be empty or truncated, never filled with guesses.
- Create requires a UUID Idempotency-Key. Scope user/method/route; retain success for 24 hours; compare normalized validated JSON, not key order. Concurrent same-key requests must serialize/replay original 201 + body/Location, including before preview-expiry validation; changed body returns 409 `IDEMPOTENCY_CONFLICT`. No mutation on that conflict. Validation/auth/provider failures are not cached successes. Different keys cannot bypass unique `(user,product)`; return 409 `DUPLICATE_TRACKED_ITEM` with the **owned** tracker ID. After retention, uniqueness still prevents duplicates. There is no guarantee about retrying a removed item after the key expires.
- PATCH changes only supplied target/enabled/preferences; supplied alerts contains both booleans. Last accepted write wins. Identical target updates do not start another episode; actual target changes allow new evaluation on a successful check, not a claimed new sale. Channel toggling/enabling does not replay old episodes; disabling/deleting cancels unsent deliveries but cannot recall externally accepted messages. Follow [the exact episode/channel rules](../project.md#alert-rules-do-not-send-the-same-alert-every-day), including uncertain-email reconciliation. A target edit never creates history or proves a discount.

### Internal email adapter outcomes

`apps/api/src/emails.ts` outcomes are internal, not new public response schemas. The current Resend SDK does not expose verified HTTP status for JSON errors, so provider error bodies cannot establish permanent or definitely retryable failure. A nonblank message ID without an SDK error means provider acceptance, not mailbox delivery. Every unconfirmed send remains `unknown`; only local pre-send validation/configuration failures are `permanent_failure`. The union reserves `retryable_failure` for a future transport with verified evidence; the current adapter does not emit it.

Retries are limited to three same-payload, same-key attempts per call (five-second timeout per attempt). Actual response `Retry-After` headers are honored, including on unknown outcomes: a delay above the one-second inline-wait limit stops retries and returns `retryAfterMs`. Integration must persist delivery keys and first-attempt times, honor that delay, preserve uncertainty across calls/restarts, and reconcile unknown deliveries rather than treating them as unsent. Never blindly retry outside Resend's documented 24-hour key window. Durable claims/recovery and public generic account responses remain the caller's responsibility. See [email setup and template activation caveats](../../README.md#resend-email-setup).

## Devices, push and admin status

Device operations require native bearer auth and current-session ownership. `installationId` is a random local UUID, never an owner credential. Register/rebind atomically on login/account switch; rotation keeps device ID. Binding uniqueness on token/installation removes previous session delivery eligibility, without exposing the previous account. DELETE only affects current-session devices. Logout/reset/expiry deactivate bindings; permission denial/removal should unregister while authenticated. Clean up invalid FCM tokens. Checking token possession/FCM validity remains backend integration work; token registration does not prove delivery.

For permission-denial cleanup after a process restart loses the server device ID, call bodyless `DELETE /api/devices/installation/{installationId}` with the still-current mobile bearer. Do not register again merely to discover an ID: that would temporarily restore delivery eligibility. This additive route normalizes UUID case (including v4/v7) and atomically matches **user + current session + installation**. It returns an empty 204 for removal, absence, foreign ownership or another/rebound session, without disclosing existence or metadata. A stale session's cleanup cannot delete a new binding. Invalid UUID or any query is 422; any submitted body is 400. Web cookies, mixed credentials, revoked/unverified sessions and origin restrictions use the existing native auth policy; the ordinary 120/minute/session limit applies once. Existing `DELETE /devices/{id}` remains 404 for missing/foreign IDs. No schema migration or new index is required.

`PushEvent` is a versioned **FCM data object with only string values**:

```json
{"schemaVersion":"1","type":"price_target_reached","eventId":"episode_example","deliveryId":"delivery_push_example","recipientSessionId":"session_example","trackedItemId":"tracker_example","productId":"product_1","observedAt":"2026-10-26T16:34:42.829Z"}
```

No arbitrary URLs, credentials, price/target or personal data. Stable `eventId` identifies the qualifying episode across channels/retries; stable `deliveryId` identifies the durable push delivery, never a fresh retry ID. Server delivery fan-out uses a per-recipient-session payload with the same event/delivery IDs; retries must not retarget a newly signed-in session. Client validates schema/type and active `recipientSessionId`, ignores unknown versions and old sessions, deduplicates durably by **recipientSessionId + eventId**, and opens only the owned tracker after an authenticated API fetch. A foreign/deleted tracker or expired session shows a safe unavailable/sign-in state. No blind URL navigation or automatic account switch. Data-only handling should avoid automatic OS presentation of sensitive stale-account content; foreground/background/tap behavior and actual delivery still need separate Android proof.

Admin enqueue accepts only `{}` and calls the same daily worker service. Ordinary users get 403 from admin batch routes; their separate owned refresh is limited to one tracked Product. Coalesce overlapping active admin/scheduled runs; enforce shared cache/backoff/claims. Admin status exposes aggregate counts only. `queued` has null started/finished timestamps; `running` has startedAt and null finishedAt; terminal states have both. `succeeded` means no failed products, `partial` means both success and failure, `failed` means no success or fatal run failure. At termination succeeded + failed + skipped = total; while active this sum may be smaller. Zero products may succeed with zero counts. Failed runs do not imply all product prices became unavailable. Poll active runs no faster than 5 seconds/Retry-After. No separate worker, scheduler, delivery service or fake outbox is added for #69.

## Errors, limits and retries

Every application error uses only:

```json
{"error":{"code":"VALIDATION_ERROR","message":"Check the highlighted fields.","fields":[{"path":"/targetPrice/amountMinor","code":"out_of_range","message":"Use nonnegative integer USD cents."}],"requestId":"request_example","retryAfterSeconds":null,"resourceId":null}}
```

See each OpenAPI operation for statuses. 400 is malformed JSON/token/auth ambiguity, 401 authentication/session loss, 403 CSRF/origin/verification/admin denial, 404 missing/foreign, 409 duplicate/idempotency/device conflict, 410 expired owned preview, 422 strict validation/unsupported/missing offer/cursor, 429 local/provider limit, 503 source/service outage. For game preview without a retained quote, unsupported URL/product, ambiguous match and missing Steam offer are 422; provider unavailability is 503; provider throttling is 429 with `Retry-After`. A validated retained quote may instead be returned stale with failure metadata. These failures do not become a zero price or a sample result. Every operation explicitly declares 500 `INTERNAL_ERROR` (no stack traces); body-bearing operations also declare 413 `PAYLOAD_TOO_LARGE` and 415 `UNSUPPORTED_MEDIA_TYPE`, each with a status-specific envelope schema. Bodyless routes reject submitted bodies with 400 rather than interpreting their media type. `fields` is always present, usually empty; paths are JSON pointers (`/query/limit` or `/headers/Idempotency-Key` outside body). `resourceId` is null except an owned duplicate tracker; request IDs contain no secrets. Error messages are human-facing; branch on code, not English text. Reverse proxies must be configured to preserve this error format; an HTML/network response is a transport failure, not a valid API response.

Proposed initial limits (implementation must enforce and tune only through documented policy): auth/register/resend/forgot/reset/verify **5 attempts per 15 minutes per IP + normalized email/token hash**, login additionally per account; CSRF bootstrap 60/minute/IP; ordinary authenticated API 120/minute/session; preview 5/minute/user and 20/minute/IP, maximum 2 concurrent/user, 10-second total deadline; manual admin enqueue 1/minute/admin; owned refresh cooldown 60 seconds per tracker after completion; admin status polling max 12/minute/admin. Provider-wide limits are shared across all entry points and may be stricter; honor upstream Retry-After rather than probing around a block. Generic account responses do not reveal which account-specific limiter fired. No paid fallback/IP rotation.

429 always includes positive integer delta-seconds `Retry-After` matching `error.retryAfterSeconds`; 503 includes both when retry is known, otherwise null/no header. Clients honor the larger local/provider wait, use bounded jittered retries, and do not busy-loop. Automatically retry safe GETs only (max two retries); retry create only with identical body + original Idempotency-Key after uncertain outcome. Do not automatically retry login/email/token consumption, PATCH, DELETE, or refresh enqueue; reconcile the returned `Location` with an owned status GET. Repeated explicit PATCH of identical values is semantically safe, but must not replay an alert. A failed fetch never masquerades as a sample/live success.
